# Shared production analysis for BAU 2040 and Fast Track 2040

## Purpose and comparative design

This specification defines one parameterised analysis pipeline for the later BAU 2040 and Fast Track 2040 production runs. The scenario ID selects only the approved config, run identity and output directory. Metric definitions, territorial scope, scaling, late window and quality gates are identical. No BAU--Fast Track comparison is produced here; comparison is released only after both production runs and both scenario analyses have independently passed.

The pipeline consists of `Production2040AnalysisSpec`, `Production2040AnalysisListener`, `AnalyzeProduction2040Output`, `Production2040VehicleMetrics` and `ValidateProduction2040AnalysisOutput`. A future runner installs the listener with `Production2040AnalysisListener.install(controler, "BAU")` or `"FAST_TRACK"`. The postprocessor and validator each accept exactly one of those scenario identifiers. None of these read-only entry points starts Controller or QSim.

## Simulation population and territorial analysis population

The simulation retains the complete regional five-percent population. This is necessary because trips outside Munich still affect congestion, routes and public-transport operations. The central result sample is narrower: a main trip is included only if both its origin main activity and destination main activity are inside or on the Munich municipal boundary (`BOTH_INSIDE`). The established boundary predicate is `covers`, and the canonical UTF-8/LF SHA-256 must remain `EFBC37F0627F94D95DAB67D1C5A2B9D05507DC9E8C9492A98A35BFF4A4AE2A26`.

MATSim's stage-activity identifier is used when trips are constructed. Public-transport interactions and transfers therefore remain parts of one main trip. The standard MATSim analysis main-mode identifier assigns `car`, `pt`, `bike` or `walk`. Any other main mode is reported and causes validation to fail; it is never silently reassigned. Missing or non-finite endpoint coordinates also fail validation.

The historical 160,603 `BOTH_INSIDE` trips describe the 2019 calibration sample only. The 2040 denominator is derived separately from each final scenario population. BAU and Fast Track may consequently have different absolute trip counts because their approved populations differ.

## Iteration statistics and stability

The runtime listener records a compact selected-plan snapshot at every iteration from 0 through 60. It writes no additional large events file. Each snapshot contains the `BOTH_INSIDE` denominator, counts and unscaled shares for the four main modes, and any unexpected modes. In parallel it counts all PersonStuckEvents, events affecting persons with at least one `BOTH_INSIDE` trip, and unique affected persons by iteration and leg mode.

Iterations 51--60 are the binding late window. For every main mode the pipeline reports mean, minimum, maximum, range and an ordinary least-squares linear trend in percentage points per iteration. The common transparent quality bounds are an absolute trend below 0.10 percentage points per iteration, a range no greater than 2.0 percentage points and a maximum late iteration-level stuck-person incidence no greater than 0.10% of the `BOTH_INSIDE` denominator. These are project criteria, not universal MATSim thresholds.

The listener writes recoverable intermediate CSVs below `analysis-runtime/`. They are not final results. The postprocessor validates the complete run and constructs all ten final files in memory before atomically publishing a new `analysis/` directory. It refuses to overwrite an existing analysis directory.

## Trips, modal split, Pkm and travel time

Final modal split uses all final selected-plan `BOTH_INSIDE` main trips. Trip counts are shown at sample scale and expanded by factor 20; shares are not scaled. The four counts plus unexpected modes must reconcile exactly with the observed scenario-specific denominator.

Distance and time measurements use MATSim's final standard `output_trips` records, matching the validated Round-5 definition. `traveled_distance` is the complete routed main-trip distance, summed across its legs. For a PT main trip it includes access walk, in-vehicle legs, transfer walk and egress walk. It is not Euclidean distance, pure in-vehicle PT distance or an event-derived distance. Missing values are reported; no straight-line substitute is invented. Each main mode reports sample and expanded Pkm, Pkm share, mean and median main-trip distance, mean travel time, record coverage and the missing/invalid record count. At least 99% mode-specific measurement coverage is required. Shares, means, medians and travel times are never multiplied by 20.

## Private-car vehicle-kilometres

Car Fkm are streamed once from the final events file against the network actually written by the run. A `VehicleEntersTraffic` event contributes the remaining fraction of the first link, every `LinkEnter` contributes that link exactly once, and `VehicleLeavesTraffic` removes the untravelled fraction of the final link. This is the relative-position convention implemented by MATSim 2025.0 and prevents first-/last-link omission and person-event double counting.

Only non-transit vehicles whose network mode is `car` are included. Transit vehicles identified by `TransitDriverStarts` are excluded even though they use car-network links. Sample Fkm and factor-20 expanded private-car Fkm are shown separately. The number of included and unassigned vehicles and unresolved links is reported. Car Pkm/Fkm is a plausibility ratio, not an identity: passengers and vehicles measure different concepts.

## Public-transport submodes

The four principal PT route modes are `bus`, `tram`, `subway` and `rail`; established synonyms are normalised only to these explicit categories. Each `TransitDriverStarts` event must resolve to a line, route, departure and transit vehicle, and its route `transportMode` determines the submode. Facility events must resolve to schedule stops. Other valid schedule modes, such as a retained ferry service, are reported as separate rows and are never silently reassigned to a principal mode. Missing route, departure, stop or vehicle references fail validation.

For PT Pkm, main-activity-end events advance each person's final selected-plan main-trip index. Boarding and alighting events identify the actual access and egress stops used while that passenger is inside a transit vehicle on a `BOTH_INSIDE` main trip. The routed in-vehicle distance between those stops is calculated from the referenced transit route and network and accumulated by route mode. It is therefore routed in-vehicle distance between event-observed stops, not Euclidean distance or a claim about the passenger's exact within-link standing position. Access and egress walks contribute no PT Pkm, and a bus--subway transfer partitions in-vehicle Pkm between bus and subway without creating another main trip. Boardings are also reported by route mode.

PT Fkm count each transit vehicle's actual link-event distance once, regardless of its passenger count. The five-percent factor describes private demand and road capacity, while the transit schedule is supplied at full service scale. PT Fkm therefore remain at observed full-service scale and are not multiplied by 20. This distinction prevents a fictitious twentyfold multiplication of scheduled service.

- `late_iteration_statistics.csv`
- `final_main_mode_summary.csv`
- `final_pkm_by_main_mode.csv`
- `final_car_fkm.csv`
- `final_pt_pkm_by_route_mode.csv`

Every CSV identifies the scenario, sample factor, unit, observed value, expansion where methodologically applicable, coverage and definition. Intermediate data are not presented as valid final results.

## Fail-closed validation and reproducibility

Before reading results, the validator requires the approved paired production configs to pass, all protected manifest hashes and the canonical boundary hash to match, the scenario output and run ID to be exact, the output config to be semantically identical to the approved config, and the log to contain normal-shutdown evidence. The shared post-run comparison recognizes only MATSim 2025.0's exact thirteen-parameter default `swissRailRaptor` serialization when the approved input config contains no explicit module; all other module, parameter and parameter-set differences fail. This narrowly defined runtime serialization rule is also used by smoke-output recovery, while every pre-run comparison remains strictly unchanged. The validator requires final plans, trips, events, network, schedule and transit vehicles; iterations 0--60; the complete late window; and one compact stuck summary for every iteration. It rejects smoke, calibration and wrong-scenario outputs by exact path, run ID and config identity.

Final checks cover selected-plan structure and coordinates, mode and trip sums, finite non-negative Pkm/Fkm, coverage, PT references, separately reported non-principal PT route modes, stuck incidence and protected-input hashes before and after analysis. Final publication is atomic and refuses overwrite. The production configs already write final events, plans and trips at normal shutdown under MATSim 2025.0; no config or behavioural parameter change was required.

The Round-5 iteration artifact is used read-only as regression evidence. The common trend/statistics implementation reproduces its documented late modal means. No calibration output is changed or republished. Local fixture tests do not execute a production postprocessor; completed production evidence is processed only through the controller-free server entries below.

These 2040 results remain scenario projections transferred from the frozen 2019 behavioural calibration. They are not recalibrated against unavailable 2040 observations, and remaining calibration and distance limitations continue to constrain absolute interpretation.

## Runner integration and recovery

`RunMatsim2040Production BAU|FAST_TRACK` is the only full-run entry point. It loads the corresponding approved config without overrides, installs the project's established SwissRailRaptor module, and calls `Production2040AnalysisListener.install(controler, scenario)` exactly once. After normal Controller shutdown it runs the common postprocessor and then validates the published analysis package. A PASS is emitted only after all three stages have succeeded.

Smoke runs use the same scenario network, schedule, vehicles, routing, scoring, QSim and time settings but iteration 0 and four in-memory technical agents. Their automatic smoke validator is separate from this scientific pipeline: smoke modal shares, trip totals, Pkm and Fkm are not research results and must never enter a BAU--Fast Track comparison.

`AnalyzeExistingMatsim2040ProductionOutput BAU|FAST_TRACK` is the recovery entry point. It has no Controller or QSim path. It accepts only a normally completed output with the exact approved run ID and output config, complete iterations 0--60, complete runtime listener evidence and protected hashes. If no final analysis exists, it reruns postprocessing once; if a complete analysis exists, it validates it without overwriting. Partial or contradictory publication remains fail-closed and must be investigated rather than silently replaced.

The Markdown report uses the same deterministic, human-readable scenario heading in generation and validation: `# BAU 2040 production analysis` or `# FAST TRACK 2040 production analysis`. CSV files retain the machine-readable identifiers `BAU_2040` and `FAST_TRACK_2040`. Exact heading validation prevents mixed or stale reports while avoiding a false rejection caused by comparing the human-readable heading with the underscore-form CSV identifier. This correction is post-processing-only and permits controller-free validation of an already published, otherwise valid analysis package.

The comparison stage remains unreleased until both independently produced and validated analysis packages exist. BAU is completed and validated before Fast Track is started, so server contention cannot become an undocumented scenario difference.

## Accounting-scope extension

The controller-free `AnalyzeProduction2040AccountingScopes` extension reads an already validated production output and applies the same code to BAU and Fast Track. `P9 Analyze Existing BAU 2040 Accounting Scopes` and `P10 Analyze Existing Fast Track 2040 Accounting Scopes` are thin, argument-free server entries. They neither construct a Controller nor alter a simulation output. Each refuses an existing target and atomically publishes nine files through a temporary sibling directory under `analysis/accounting_scopes` only after all checks pass.

Three accounting concepts are deliberately separated. `BOTH_INSIDE` contains selected-plan MATSim main trips whose origin and destination main activities are covered by the canonical Munich municipal boundary. `MUNICH_RESIDENTS` contains every main trip of a person whose first documented selected-plan activity of type `home` is a non-stage activity with a finite coordinate covered by that boundary; this includes trips between Munich and the surrounding region. A trip origin is never used as a proxy for residence. Persons without such a home are reported as `UNRESOLVED` and excluded from the resident cohort. Resident, non-resident and unresolved person and trip totals remain visible. Both demand scopes exclude stage activities and accept only the common transport-planning main modes `car`, `pt`, `bike` and `walk`.

Modal split and expanded demand trip counts use the complete structural final selected-plan index. Standard `output_trips` rows are then matched by person ID and one-based trip number; every available row must have an indexed key, the same main mode and the same endpoint category, and duplicates or extra rows fail. The standard output-trip file need not contain a distance/time measurement for every structural selected-plan trip. This is reported neutrally as “standard output-trip measurement not available for every structural selected-plan trip”; it is not described as stale unless independent evidence proves that cause. Available-row coverage and valid routed distance/time coverage are both validated overall and for every applicable `BOTH_INSIDE`/`MUNICH_RESIDENTS` by-mode cell against the existing minimum of 99%. Exactly 99% passes; lower coverage fails. Pkm, mean and median distance, and travel time use only valid `output_trips` measurements, while modal shares and factor-20 trip counts continue to use structural selected-plan trips. The quality file and Markdown report expose structural, measured, missing and coverage counts by scope/mode as well as missing indexed trips by endpoint category and resident status. `traveled_distance` remains the complete routed main-trip distance, including PT access, egress and transfers. Missing distance is never replaced by a beeline. Bike-km is explicitly derived as bike Pkm under a one-person-per-bike convention. Walk remains Pkm and is never described as vehicle-kilometres.

Private-car Fkm use the existing event-distance implementation through a shared movement observer, so the MATSim 2025.0 first-/last-link convention is not reimplemented. Every private-car traffic segment must resolve to its traffic person and current selected-plan main trip. Transit vehicles are excluded. Endpoint-category car distances must sum to the unchanged regional `final_car_fkm.csv`, and unassigned persons, trips, vehicle transitions, incomplete segments, missing links or other ambiguity prevent publication. The resulting car-Pkm/Fkm ratio is a plausibility ratio and is not interpreted as occupancy. The original regional car Fkm file remains valid for regional simulation movement but is unsuitable for a `BOTH_INSIDE` external-cost calculation because it is not trip-scope restricted.

PT vehicle service cannot be assigned uniquely to `BOTH_INSIDE` or resident passengers: one vehicle movement simultaneously serves passengers from several cohorts and trip scopes. `TERRITORIAL_PT_SERVICE` therefore clips final transit-vehicle event distance to the Munich territory. For ordinary links with finite, positive straight node-to-node geometry, a segment fully inside the polygon receives its full MATSim link length, a segment outside receives zero, and a crossing link receives its MATSim length multiplied by the exact fraction of the straight node-to-node geometry intersecting the polygon. No midpoint approximation is used.

MATSim PT networks can also contain valid positive-model-length pseudolinks whose from-node and to-node have the same finite coordinate. They have no encoded spatial extent and therefore cannot be geometrically clipped. For these links only, the analyzer uses an explicitly labelled point-anchor proxy: a strictly interior anchor assigns the full MATSim model length, an anchor outside and not covered by the municipal polygon assigns zero, and an anchor exactly on the boundary stops publication as spatially ambiguous. Non-finite coordinates and negative or non-finite model lengths also fail. A zero-model-length PT link is reported separately and contributes zero territorial distance. The proxy preserves the PT service event distance and the uncut regional reconciliation; it is a necessary modelling proxy, not a claim that the link has a geometrically known extent. Reports state the number of used point-anchored pseudolinks, their uncut model length, inside/outside classifications, proxy-assigned territorial service and its share of territorial PT Fkm.

A read-only protected-network inventory found 4,362 zero-geometry links in BAU (4,353 positive-length 50 m PT pseudolinks and nine zero-model-length links) and 4,367 in Fast Track (4,358 positive-length 50 m PT pseudolinks and nine zero-model-length links). The inventory records each link ID, model length, allowed modes and anchor coordinate. For example, `pt_4192` is a 50 m `pt` link from and to `pt_102065` at `(4414786.48, 5327680.14)` in both protected networks. The first BAU P9 attempt stopped before publication because the prior code incorrectly rejected that valid self-loop; no simulation output or protected input was changed, and QSim is not repeated. Before territorial classification, every route-mode total must reproduce the unchanged regional `final_pt_fkm_by_route_mode.csv`. Bus, tram, subway and rail are explicit; ferry and other documented modes are grouped transparently. PT supply is simulated at full service scale and is never multiplied by 20.

Private-demand daily counts, Pkm, bike-km and car Fkm are expanded from the five-percent sample by factor 20. Modal and Pkm shares, mean and median distance and mean travel time remain unscaled. PT service is full-scale. Each applicable table also labels a mechanical `illustrative_annual_equivalent_365_days`. The GTFS/MATSim run represents a technical weekday; multiplication by 365 is not an empirically validated annualisation and must not be cited as an authoritative annual total.

The extension writes `accounting_scope_definition.csv`, `final_modal_split_by_scope.csv`, `final_pkm_by_scope_and_mode.csv`, `final_private_car_fkm_by_scope.csv`, `final_active_mode_distance_by_scope.csv`, `final_territorial_pt_fkm_by_route_mode.csv`, `resident_cohort_summary.csv`, `accounting_scope_quality_checks.csv` and `accounting_scope_report.md`. Existing production-analysis files and regional Fkm files are never overwritten. BAU and Fast Track must be run separately through P9 and P10; scenario identity, complete standard outputs, normal shutdown, protected hashes, regional reconciliation and the canonical boundary remain fail-closed gates. No simulation is repeated.

## PT cost-allocation extension

`AnalyzeProduction2040PtCostAllocation` is a second, controller-free extension that consumes an already validated production-analysis package and an already validated `accounting_scopes` package. `P11 Analyze Existing BAU 2040 PT Cost Allocation` and `P12 Analyze Existing Fast Track 2040 PT Cost Allocation` are thin, argument-free server entries. They write only a new protected `analysis/pt_cost_allocation` directory and refuse an existing destination. They never construct a Controller or QSim and never change a population, network, schedule, vehicle file, GTFS input, production config, existing analysis, or Excel workbook.

The missing demand quantity is territorial all-passenger in-vehicle Pkm. It is reconstructed while streaming the final events once. After `TransitDriverStarts`, the route `transportMode` is normalised by the existing bus/tram/subway/rail mapping; other modes remain a transparent `ferry/other` group with their normalized component modes listed in the output. `PersonEntersVehicle` and `PersonLeavesVehicle` maintain the actual onboard passenger set. The transit driver is excluded by the driver ID from `TransitDriverStarts`. No selected-plan endpoint, resident, home-location, or person-index filter is applied to this new quantity, so non-residents and persons with unresolved homes are included when they ride PT.

For each transit link movement, only passengers on board for that event receive the movement. The passenger movement uses the same final-event first-/last-link convention as PT Fkm. In particular, a `VehicleLeavesTraffic` correction is applied to the passenger snapshot from the original movement, not to a later onboard set. This avoids a correction based on passengers who boarded or alighted after the movement. Transfers are independent actual boardings on their vehicle and route mode; access, egress, and transfer walking are never counted as PT Pkm. Repeated route-link occurrences and direction are retained because the final event stream, rather than a deduplicated route-link set, is used.

Territorial clipping reuses `Production2040AccountingEventMetrics.clip`: ordinary links use exact line/polygon intersection fractions, boundary-crossing link distance is apportioned by that fraction, and positive-length zero-geometry PT pseudolinks use the existing strict point-anchor treatment. A point anchor exactly on the boundary fails. Zero-model-length PT links are reported and contribute zero. There is no Euclidean, midpoint, or whole-route fallback when a used link, transit reference, or spatial assignment cannot be resolved.

For scenario `s` and normalized route mode `m`, the package applies the following equations without rounding intermediate values:

`occupancy(s,m) = expanded territorial all-passenger Pkm(s,m) / territorial full-service Fkm(s,m)`

`allocated BOTH_INSIDE Fkm(s,m) = expanded BOTH_INSIDE in-vehicle Pkm(s,m) / occupancy(s,m)`

The all-passenger Pkm sample is expanded exactly once by 20. Territorial PT Fkm is read from the existing validated accounting-scope result and remains at full service scale; it is never multiplied by 20. The existing `final_pt_pkm_by_route_mode.csv` supplies the unchanged scenario-specific BOTH_INSIDE in-vehicle Pkm definition: event-observed boarding/alighting stops, transit-route in-vehicle distance, no walking, and full retained in-vehicle distance even where a qualifying trip travels outside Munich. Source Pkm and source territorial Fkm are independently reconstructed and reconciled before allocation. Uncut regional PT Fkm is reconciled by the established accounting event validator. Reconciliation uses the existing `1e-3` metre tolerance; no new distance tolerance is introduced.

A zero territorial Fkm denominator with zero territorial and BOTH_INSIDE demand is an explicit valid zero-activity case: occupancy and allocated Fkm are `NOT_APPLICABLE`, rather than invented zeros. A zero denominator with passenger activity, or zero occupancy with non-zero BOTH_INSIDE demand, fails publication. A positive supply denominator with no passenger demand is reported as a valid zero-passenger-activity case. Allocated Fkm is not capped at territorial Fkm. It is an accounting allocation under the assumption that BOTH_INSIDE travellers use the average territorial occupancy for their route mode, including any outside-Munich in-vehicle portion retained in the BOTH_INSIDE numerator. It is not a marginal or avoidable-service estimate.

Each scenario receives four compact files under `analysis/pt_cost_allocation/`: `pt_external_cost_inputs.csv`, `pt_cost_allocation_quality_checks.csv`, `pt_vehicle_unit_metadata.csv`, and `pt_cost_allocation_report.md`. The input CSV provides sample and factor-20-expanded territorial Pkm, full-service territorial Fkm, occupancy, source BOTH_INSIDE Pkm, allocated Fkm, mechanical 365-day equivalents, and Pkm/allocated-Fkm millions per year for Excel. Values are stored from the calculation doubles without display rounding. Its status and boarding/coverage columns distinguish direct event transport activity, expanded demand estimates, occupancy, accounting-allocated Fkm, and annualized values. All occupancy values are reported separately for manual review; no capacity threshold is used.

`pt_vehicle_unit_metadata.csv` lists the vehicle types used by schedule departures, their normalized route modes, scheduled vehicle/departure counts, available capacity and physical metadata. A read-only input inspection found that both current transit-vehicle files define `defaultTransitVehicleType` with 101 seats, zero standing room, 7.5 m length, passenger-car equivalent 1.0, and network mode `pt`. This generic MATSim metadata does not identify bus bodies, tram sets, subway trains, rail consists, or carriage counts. An Fkm is therefore one event-observed MATSim transit-vehicle trajectory kilometre for a scheduled vehicle ID. The package explicitly does not infer a train-to-carriage conversion or assume that a MATSim vehicle ID is the vehicle unit required by an Excel factor. Capacity is descriptive only and is not compared with expanded occupancy; an external unit mapping is required before a vehicle-unit-specific cost factor is transferred to Excel.

The approved production configs, protected manifest inputs, and canonical municipal boundary must also remain at their contract paths. P11 analyses `scenarios/munich_bau_2040/output/production-mode-choice`; P12 analyses `scenarios/munich_fast_track_2040/output/production-mode-choice`.

Run P11 once for BAU and P12 once for Fast Track only when the corresponding `analysis/pt_cost_allocation` destination is absent. A failed run publishes no partial package; its guarded temporary sibling is removed. If the destination already exists, do not rerun or delete it: preserve it as evidence and use the read-only `ValidateProduction2040PtCostAllocation BAU|FAST_TRACK` class if a separate validation is needed. Copy the four files from each resulting `analysis/pt_cost_allocation/` directory back to the local repository. A local machine that contains only copied analysis CSVs and lacks the complete final production files cannot execute this analyzer; fixture tests are verification of the implementation, not a claim that real production data was processed locally.

## Territorial external-cost transfer-table extension

`AnalyzeProduction2040TerritorialCostInputs` is a third, controller-free extension for the completed BAU and Fast Track production outputs. Its two argument-free IntelliJ server configurations are `Analyze Existing BAU 2040 Territorial Cost Inputs` and `Analyze Existing Fast Track 2040 Territorial Cost Inputs`. One shared parameterised implementation selects only the production scenario identity and its canonical output directory. It never creates a Controller or QSim, rebuilds no input, and refuses to overwrite an existing `analysis/territorial_cost_inputs` destination.

The purpose is a transfer table for a municipal external-cost comparison. Its spatial rule is territorial rather than person or trip based: count the fraction of every eligible movement physically inside the canonical Munich municipal boundary in the established projected CRS, irrespective of a person's residence, home availability, trip origin or destination. An outside-to-outside movement crossing the municipal boundary contributes its inside fraction. This is an additional accounting perspective, not a replacement for the existing `BOTH_INSIDE` selected-plan analysis or the documented-Munich-resident analysis. The calibration target remains an endpoint-based `BOTH_INSIDE` trip measure while the external-cost table is boundary-distance based; that existing calibration/accounting mismatch, including the resident-target limitation, remains visible and unresolved rather than being silently harmonised.

The analyzer accepts only a normally completed production output with the exact scenario run ID, output config, final iteration 60 root files, validated production analysis, validated accounting-scope package, validated PT cost-allocation package, protected hashes and canonical municipal-boundary hash. It reads the one root final events file only, never an `ITERS` copy, so final events are not summed across iterations or duplicated. The reporting day remains the established technical weekday convention. The event horizon can extend beyond 24 hours, and the file is one simulated reporting-day realization rather than a sequence of independent daily observations.

Private-car Fkm is streamed once from final events through the established first-/last-link movement convention. Only non-transit vehicles whose actual network mode is `car` enter Car; transit vehicles are excluded through the established vehicle classification, and every other observed non-transit network vehicle category is reported separately in the workbook definitions instead of being reassigned to Car. Each modeled car movement receives the established link clipping fraction. Observed movement before a `PersonStuckEvent` remains included, but no untravelled route remainder is inferred. The uncut event total must reconcile to the established regional car Fkm. Territorial car Fkm is multiplied by 20 once, and car Pkm is then explicitly derived as Fkm times the external assumption of 1.5 persons per car; it is not observed passenger movement.

PT is transferred directly from the validated `analysis/pt_cost_allocation/pt_external_cost_inputs.csv`, whose territorial all-passenger in-vehicle Pkm includes every actual non-driver passenger and excludes drivers, access, egress and transfer walking. The analyzer reconciles the transferred full-service Fkm by route mode with the validated `analysis/accounting_scopes/final_territorial_pt_fkm_by_route_mode.csv`. Bus, tram, subway and rail appear separately; a nonzero other group appears explicitly with its normalized component modes. Territorial passenger Pkm is expanded from the five-percent demand sample exactly once, while service Fkm remains full-service and receives factor 1. Mode-specific occupancy is expanded Pkm divided by unscaled service Fkm, with valid zero-demand/supply cases shown explicitly. The prior allocated `BOTH_INSIDE` Fkm fields are deliberately not used in this table.

The validated PT source retains the established clipping treatment: ordinary links use geometric line/polygon fractions, positive-model-length links with coincident endpoint coordinates use the documented strict point-anchor proxy, and zero-model-length links contribute zero. The workbook reports the proxy-assigned service share. A PT Fkm is a MATSim scheduled-vehicle trajectory kilometre; no train-to-carriage conversion or external Excel vehicle-unit mapping is inferred. Therefore the transfer table retains a visible `REQUIRES_EXTERNAL_UNIT_MAPPING` warning for vehicle-unit-specific costing.

The actual final output config is checked to confirm that walk, bike and `non_network_walk` are teleported. For each completed active leg, territorial distance is the modeled leg distance multiplied by the fraction of the straight segment between that leg's own endpoints inside the boundary. This is a transparent spatial approximation, not a claim that a teleported leg followed that line. The modeled distance already embodies the configured routing/beeline convention, so no beeline factor is applied a second time. Walking access, egress and transfer legs are counted under Walk rather than PT Pkm; the definitions sheet separates completed walking distance in main-mode walk trips from walking stages in other main-mode trips. A planned leg without completed event evidence is not treated as traveled; missing modeled distances, missing coordinates, positive-distance coincident endpoints, incomplete/stuck legs and coverage remain reported as unresolved rather than replaced with zero. Bike Fkm is an explicit one-person-per-bike derivative; Walk has no Fkm or occupancy.

Each passed scenario receives exactly one XLSX file and no CSV/map/dashboard exports:

- `scenarios/munich_bau_2040/output/production-mode-choice/analysis/territorial_cost_inputs/BAU_2040_territorial_cost_inputs.xlsx`
- `scenarios/munich_fast_track_2040/output/production-mode-choice/analysis/territorial_cost_inputs/Fast_Track_2040_territorial_cost_inputs.xlsx`

The workbook has only `Inputs` and `Definitions_and_checks` sheets. `Inputs` contains Car, Walk, Bike, Bus, Tram, Subway, Rail, any nonzero Other PT group, a visibly marked mixed-unit PT subtotal, and an all-mode Pkm total that does not add that subtotal a second time. Daily values are full-scale numeric Excel cells ready for transfer, are formatted without scientific notation, and remain unrounded in the stored calculation values. Mechanical annual equivalents are daily values times 365 divided by 1,000,000; they are not observed annual traffic. Fkm are never summed across cars, bikes and different PT vehicle units into an all-mode Fkm total. Publication first writes and reopens a temporary workbook, checks numeric cells, totals, formulas and absence of external workbook links, and only then atomically moves the one-file directory into place.

Before server execution, retain the same complete final production files required by P11/P12: normal-shutdown log, final output config, final plans, events, network, schedule and transit vehicles, runtime iteration/stuck evidence, the ten-file `analysis/` production package, the nine-file `analysis/accounting_scopes/` package, and the four-file `analysis/pt_cost_allocation/` package. The final output directory must not already contain `analysis/territorial_cost_inputs/`. Fixed noise, infrastructure and any other non-distance external costs require separate assumptions outside this analyzer. It covers the four modeled modes Car, Walk, Bike and PT service/passengers, not all transport activity in Munich. Local fixture tests and compilation verify implementation only; they do not constitute a local analysis of copied or incomplete production evidence.
