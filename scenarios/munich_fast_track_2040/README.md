# Fast Track 2040 scenario

Fast Track starts from the same common-measures BAU GTFS and then adds U9, the U4 extension and two Nordring services associated with infrastructure that could be accelerated for a hypothetical Munich Olympic Games. The four-track Daglfing–Johanneskirchen measure is only an enabling condition; physical rail capacity is not represented. Existing S8 service remains unchanged.

The contract-compliant production config is `config_fast_track_2040_mode_choice.xml`. It is generated through the MATSim Config API from the same frozen Round-5 calibration config as BAU. It references the validated Fast Track network, schedule and vehicles under `input_transit/` and the scenario-specific `population_2040_fast_track.xml`. The latter is reproducibly derived from the unchanged common `population_2040.xml` by `CreateFastTrackVillagePopulation2040`: existing persons are relocated to Olympic Village and Media Village demand coordinates, without creating agents or changing times, modes, plan structures or person attributes. The BAU population remains unchanged. The historical `config_fast_track.xml` remains a legacy technical config and is not production-ready.

The village representation is deliberately limited to relocated `home` and `work` activities on existing car links. It does not create buildings or roads and does not yet distinguish permanent residents, Games-time accommodation, media employment or visitors. See the [population methodology](../../docs/methodology/population_2040.md) and the [authoritative transit-input methodology](../../docs/gtfs2040/matsim_2040_transit_inputs.md).

Twelve Fast Track Mobility Hubs are implemented as a separate analytical assumption: four large, four medium and four small hubs. The final schedule post-processor reads the versioned specification and changes exactly 790 existing directed cross-stop transfer times, with class reductions of 20%, 15% and 10% and a 60-second floor. It retains all 95,912 transfer relations and excludes 103 self-relations. The step is Fast-Track-only and passed focused tests, full input readback and a two-person iteration-zero smoke test. Shared mobility, parking, physical construction and public-space quality are not represented. See the [Mobility Hub methodology](../../docs/methodology/mobility_hubs_fast_track.md).

BAU and Fast Track use identical behavioural parameters and are not recalibrated against unavailable 2040 observations. The complete regional population remains in the simulation. The `BOTH_INSIDE` Munich filter is applied only by the later comparative analyzer; it does not filter this production population. Config generation and read-only validation have completed without starting Controller or QSim. See the [production scenario contract](../../docs/methodology/production_2040_scenario_contract.md).

The shared, scenario-parameterised [production analysis method](../../docs/methodology/production_2040_analysis.md) and server runner are prepared but have not been run locally. `P2 Validate Fast Track 2040 Production Input` is read-only and remains usable regardless of existing smoke or production outputs. `P4 Run Fast Track 2040 Production Smoke Test` requires both Fast Track target directories to be absent, uses four in-memory agents anchored to an actual U9 route and automatically checks PT boarding, car link events and avoidance of all thirteen pedestrian-zone restrictions; it is not a scientific run. If QSim and scoring ended normally but automatic validation did not complete, `P4B Validate Existing Fast Track 2040 Production Smoke Output` validates that preserved output read-only without repeating QSim. Before creating its Controller, `P8 Run Fast Track 2040 Production` requires the Fast Track production target to be absent and revalidates both the preserved BAU and Fast Track smoke outputs. Only after the complete BAU production run passes may P8 execute iterations 0--60. `P8B Analyze Existing Fast Track 2040 Production Output` is controller-free recovery after a normal simulation shutdown. The same listener, postprocessor, quality gates and PT route-mode definitions apply to BAU and Fast Track.

The completed server output can additionally be processed once with `P10 Analyze Existing Fast Track 2040 Accounting Scopes`. P10 invokes exactly the same controller-free code and definitions as BAU and writes only `output/production-mode-choice/analysis/accounting_scopes`. Resident classification is based on the documented final `home` activity, so Fast Track village relocations are reflected through the existing scenario population rather than a new assumption. PT service is clipped territorially and is not attributed to resident passengers. Existing regional Fkm files remain unchanged, and the completed Fast Track QSim must not be repeated.

After the validated P10 package exists, run `P12 Analyze Existing Fast Track 2040 PT Cost Allocation` once only if `output/production-mode-choice/analysis/pt_cost_allocation` is absent. P12 invokes the same controller-free code as BAU and streams the preserved final Fast Track events once to reconstruct territorial in-vehicle Pkm for every non-driver PT passenger, including non-residents and persons with unresolved homes. It preserves the scenario-specific existing BOTH_INSIDE in-vehicle Pkm, reuses territorial full-service PT Fkm, and publishes mode-specific occupancy and accounting-allocated Fkm for bus, tram, subway, rail, and transparent other modes. Demand is expanded exactly once by 20 while service is not. The result is protected under `analysis/pt_cost_allocation`; it is an accounting allocation rather than marginal avoidable service and does not authorise QSim, input, output, or Excel changes.
