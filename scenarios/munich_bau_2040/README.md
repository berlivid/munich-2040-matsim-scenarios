# BAU 2040 scenario

BAU is the reference scenario for the thesis comparison. Its GTFS is built from the cleaned Munich forecast and then adds the common Poccistraße regional stop and Berduxstraße S-Bahn stop. The Sendlinger Spange has no separate regular-day timetable modification. The technical GTFS date is 13 February 2026 and does not define the scenario year. BAU retains the unchanged common `population_2040.xml`; Fast Track derives a separate village-relocation population from that baseline. Road supply remains shared.

The contract-compliant production config is `config_bau_2040_mode_choice.xml`. It is generated through the MATSim Config API from the frozen Round-5 calibration config and differs from the Fast Track config only through the scenario identity, protected output directory and allowlisted inputs. It references `population_2040.xml` and the BAU network, schedule and vehicles under `input_transit/`. The historical `config_bau.xml` remains a legacy technical config and is not production-ready.

BAU and Fast Track use identical behavioural parameters and are not recalibrated against unavailable 2040 observations. The complete regional population remains in the simulation. The `BOTH_INSIDE` Munich filter is applied only by the later comparative analyzer; it does not filter this production population. Config generation and read-only validation have completed without starting Controller or QSim. See the [production scenario contract](../../docs/methodology/production_2040_scenario_contract.md) and the [authoritative transit-input methodology](../../docs/gtfs2040/matsim_2040_transit_inputs.md).

The shared, scenario-parameterised [production analysis method](../../docs/methodology/production_2040_analysis.md) and server runner are prepared but have not been run locally. `P1 Validate BAU 2040 Production Input` is read-only and remains usable regardless of existing smoke or production outputs. `P3 Run BAU 2040 Production Smoke Test` requires both BAU target directories to be absent, uses four in-memory agents and automatically validates its protected iteration-zero output; it is not a scientific run. If QSim and scoring ended normally but automatic validation did not complete, `P3B Validate Existing BAU 2040 Production Smoke Output` validates that preserved output read-only without repeating QSim. Before creating its Controller, `P7 Run BAU 2040 Production` requires the BAU production target to be absent and revalidates both the preserved BAU and Fast Track smoke outputs. It then executes iterations 0--60, installs the common listener exactly once, postprocesses and validates the final package. `P7B Analyze Existing BAU 2040 Production Output` is controller-free recovery after a normal simulation shutdown. `BOTH_INSIDE` is applied at analysis time, iterations 51--60 form the late window, and final files are published only as one validated package.

The completed server output can additionally be processed once with `P9 Analyze Existing BAU 2040 Accounting Scopes`. P9 is controller-free and writes only the new protected `output/production-mode-choice/analysis/accounting_scopes` package. It reports `BOTH_INSIDE` demand, all trips of documented Munich residents, scoped private-car Fkm and territorially clipped PT service Fkm. It preserves the existing regional Fkm files, which describe all simulated regional vehicle movement and are not suitable for a `BOTH_INSIDE` external-cost calculation. The completed BAU QSim must not be repeated.

After the validated P9 package exists, run `P11 Analyze Existing BAU 2040 PT Cost Allocation` once only if `output/production-mode-choice/analysis/pt_cost_allocation` is absent. P11 is controller-free and streams the preserved final BAU events once to reconstruct territorial in-vehicle Pkm for all non-driver PT passengers, with no resident, home-location, or BOTH_INSIDE filter. It reuses the existing validated BOTH_INSIDE in-vehicle Pkm and territorial full-service PT Fkm to report bus, tram, subway, rail, and any transparent other-mode group, mode-specific occupancy, and accounting-allocated BOTH_INSIDE Fkm. Demand is expanded by factor 20; supply is not. The package is atomically published only under `analysis/pt_cost_allocation` and must be preserved if it already exists. It is not a request to rerun BAU QSim or alter an Excel workbook.
